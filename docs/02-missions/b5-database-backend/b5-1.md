# B5-1 — SQL Database Design

## Mission Identity

- 제목: 정보를 깔끔하게 정리하는 디지털 서랍장 만들기
- 영역: Database & Back-end
- 공식 구분: 필수
- Repository: https://github.com/MetaStudy999/codyssey-basic-b5-1-database-design
- Growth Stage: `CORE`

실제 수행 상태와 G1~G8은 `config/missions.yaml`을 Source of Truth로 사용한다.

## Core Goal

관계형 데이터베이스를 설계하고 SQL만으로 Table, Constraint, Sample Data, Query를 작성해 데이터 모델과 질의를 검증한다.

## CORE

- 4개 이상 Table과 각 PK
- FK 기반 1:N 관계 2개 이상
- NOT NULL / UNIQUE / CHECK 등 필요한 Constraint
- Table별 충분한 Sample Data
- 기본 조회 / JOIN / 집계 / Subquery / UPDATE / DELETE / Index Query
- ERD와 SQL 정의의 일관성
- 실제 Query 실행 결과 Evidence

공식 세부 요구는 Mission Source와 개별 Repository의 Evaluation을 기준으로 다시 확인한다.

## Evaluation Summary

B5-1의 평가 준비는 다음 네 축으로 정리한다.

### 1. SQL 결과물과 실제 동작

대표 평가 범위:

- 최소 4개 Table과 PK
- FK 기반 1:N 관계 최소 2개와 잘못된 참조 차단
- Table별 최소 10행 수준의 Sample Data
- 총 15개 Query 구성
  - 기본 조회 4
  - JOIN 4
  - 집계 3
  - Subquery 1
  - UPDATE/DELETE 2
  - Index 1
- 각 Query의 실제 실행 Evidence

### 2. 데이터 모델 설계 설명

- Table을 분리한 이유와 역할
- FK 기반 1:N의 실제 Domain 의미
- Column Type 선택 이유
- Index 대상 Column과 선택 이유

### 3. 관계형 DB 핵심 개념 설명

- Database와 Spreadsheet의 차이
- PK / FK / 1:N
- INNER JOIN / LEFT JOIN
- GROUP BY / COUNT / SUM / AVG

### 4. 문제 해결 설명

- 가장 복잡한 Query를 단계별로 설명
- 가장 어려웠던 설계·Query 문제와 해결 과정

## Current Implementation Example

현재 Mission Repository의 구현은 학습 도서 대여 Domain을 사용한다.

```text
categories 1 ─── N books
members    1 ─── N rentals
books      1 ─── N rentals
```

대표 구현 파일:

- `sql/01_schema.sql` — Table, PK/FK, NOT NULL, UNIQUE, CHECK
- `sql/02_seed.sql` — 관계형 Sample Data
- `sql/03_queries.sql` — Q01~Q15
- `scripts/verify.py` — Clean SQLite 재구축과 자동 검증
- `evidence/*.txt` — 실제 실행 결과

실제 Repository 상태가 변경되면 해당 Repository를 우선한다.

## 평가 답변 권장 구조

```text
개념
→ 현재 B5-1의 실제 Table / Column / Query
→ 왜 그렇게 설계했는가
→ Test / Evidence로 어떻게 확인했는가
```

예:

```text
FK는 다른 Table의 PK를 참조하는 키입니다.
현재 구현에서는 rentals.member_id → members.id가 FK입니다.
존재하지 않는 member_id를 INSERT했을 때 Constraint 오류가 발생하는지
실제 검증 결과로 참조 무결성을 설명합니다.
```

Repository에 모범답안이 존재하는 것과 학습자가 실제로 설명할 수 있는 것은 동일하지 않다. 구현·자동 검증·Evidence는 Repository에서 확인하고, 구두 설명 능력은 필요한 경우 Human Runtime에서 확인한다.
