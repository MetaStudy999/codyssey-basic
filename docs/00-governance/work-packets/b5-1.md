## 3. Mission-derived Scope

- SQLite/MySQL/PostgreSQL/H2 등 로컬 실행 가능한 DB 하나를 선택한다.
- 최소 4개 테이블을 설계하고 각 테이블에 PK를 둔다.
- 최소 2개 이상의 FK로 1:N 관계를 만든다.
- 의미 있는 데이터 타입과 역할이 드러나는 이름을 사용한다.
- 최소 1개 `NOT NULL`, 최소 1개 `UNIQUE`, 실제 동작하는 FK 제약을 적용한다.
- 각 테이블에 최소 10행 이상의 관계가 있는 샘플 데이터를 넣는다.
- 총 15개 이상의 핵심 SQL query를 작성한다.
- query 범위는 기본 조회, JOIN, 집계/GROUP BY, subquery, UPDATE/DELETE, index를 포함한다.
- Mission PDF 기준 예: 기본 조회 4+, JOIN 4+(INNER 2+, LEFT 1+), 집계 3+, subquery 1+, UPDATE/DELETE 2+, index 1+를 G1에서 재확인한다.
- 각 query에 목적 설명을 붙이고 실제 실행 결과를 screenshot 또는 text로 남긴다.
- 제출물은 schema SQL, sample insert SQL, query SQL, 실행 결과 폴더를 기본으로 한다.
- backend framework/API/UI는 이 Mission 범위가 아니다.

## 5. G2 BUILD

- [ ] 주제를 4개 테이블/2개 1:N이 자연스럽게 나오는 수준으로 제한한다.
- [ ] schema → parent data → child data → query 순으로 재현 가능한 SQL 파일을 구성한다.
- [ ] DB 전용 문법을 사용하면 해당 위치에 명확히 표시한다.
- [ ] 불필요한 ORM/framework를 도입하지 않는다.

## 6. G3 TEST

- 깨끗한 DB에서 schema 전체 실행
- PK/NOT NULL/UNIQUE/FK 실제 제약 검증
- 각 테이블 row count 10+ 확인
- 15+ query 전체 실행 성공
- JOIN/aggregate/subquery/update/delete/index 범주 충족
- FK 위반 입력이 실패하는지
- query 설명과 결과 Evidence가 1:1로 연결되는지

## 7. G4 REVIEW

- 관계가 단순 ID 저장이 아니라 실제 FK로 보장되는가
- data insert 순서가 재현 가능한가
- query 15개가 거의 같은 SELECT의 변형으로 채워지지 않았는가
- index 적용 이유가 query와 관련 있는가
- BLOCKER=0, MAJOR=0인가

## 8. G5 RUNTIME / G6 EVIDENCE
