## 2. G1 SOURCE — 첫 수행내역

- [ ] Mission/Evaluation PDF·MD·평가문항을 탐색한다.
- [ ] Repository 권한, 현재 collaborator/team 상태, default branch, branch protection, Issues/PR/Review 기록을 조사한다.
- [ ] `SUBMISSION.md`, `docs/CONTRIBUTING.md`, `docs/conflict-resolution.md`, `docs/troubleshooting-log.md` 존재/내용을 확인한다.
- [ ] 팀원별 PR/Review 최소 수량과 충돌/트러블슈팅 횟수를 Source별로 정확히 추출한다.
- [ ] 실제 GitHub 활동으로만 입증 가능한 항목을 Runtime/Evidence로 표시한다.

## 3. Mission-derived Scope

- 3~5인 팀으로 하나의 협업 Repository를 운영한다.
- `main`에 Branch Protection을 적용하고 직접 push 대신 PR 기반 병합 흐름을 사용한다.
- Issue 기반으로 작업하고 PR 본문에서 `Closes #n` 또는 동등한 방식으로 추적한다.
- 팀원별 최소 PR 생성/병합과 코드 리뷰 참여 기준을 충족한다.
- 본인 PR에서 리뷰 코멘트를 실제 수정/답글/추가 커밋으로 반영한 기록을 남긴다.
- 의도적 충돌을 만들고 팀 전체 최소 충돌 해결 횟수와 비자명 충돌 기준을 만족한다.
- `git commit --amend`, `git reset --soft`, `git revert`, `git stash/stash pop` 트러블슈팅 시나리오를 재현·기록한다.
- `CONTRIBUTING.md`, conflict resolution, troubleshooting log를 작성한다.
- `SUBMISSION.md`에서 팀원별 PR/Review/문서/Evidence를 한 곳에서 추적 가능하게 한다.
- Git graph 결과 또는 동등한 Git history Evidence를 남긴다.

## 5. G2 BUILD

- [ ] 실제 협업을 방해하지 않는 최소 결과물(유틸 함수/팀 문서/학습 노트 등)을 선택한다.
- [ ] Issue → branch → PR → review → merge 추적성을 유지한다.
- [ ] 문서 템플릿은 재현 단계, 결과, 주의점을 포함한다.
- [ ] CODEOWNERS 등 선택 기능은 필수 완료를 지연시키지 않는다.

## 6. G3 TEST / Verification

이 Mission은 코드 테스트보다 GitHub 기록 검증 비중이 크다.

- Branch Protection 설정 확인
- PR이 Issue와 연결되는지 확인
- 팀원별 PR/Review 수량 Source 기준 검증
- 리뷰 반영 상호작용 확인
- 충돌 해결 기록 수량과 비자명 충돌 조건 확인
- amend/reset/revert/stash 4종 기록 확인
- 필수 문서와 `SUBMISSION.md` 링크 유효성 확인
- Git graph Evidence 확인

## 7. G4 REVIEW

- 협업 기록이 사후 작성된 설명만이 아니라 실제 GitHub 이벤트와 연결되는가
- 본인 PR 리뷰와 타인 PR 리뷰가 구분되는가
- 충돌/트러블슈팅이 재현 가능한가
- Branch Protection이 실제 main 정책에 적용되어 있는가
- BLOCKER=0, MAJOR=0인가

## 9. G7 LEARN

- branch가 commit을 가리키는 포인터인 이유
- GitHub Flow와 PR 목적
- 코드 리뷰 가치
- conflict marker와 해결 흐름
- reset/revert/stash/amend 차이
- 재현 가능한 협업 기록의 가치

`HANDOFF.md`, `mission-result.yaml`에 팀원별 검증표, 실제 GitHub 링크, Source/Evaluation 기준, 충돌/트러블슈팅 Evidence, final merge 상태를 기록한다. 대표 Repository는 수정하지 않는다.
