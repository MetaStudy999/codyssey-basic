## 3. Mission-derived Scope

- OOM Crash, CPU Latency/과점유, Deadlock 3가지 장애를 각각 재현·분석한다.
- 제공 앱의 일반 사용자 실행, `AGENT_HOME`, `AGENT_PORT=15034`, upload/key/log 경로 등 사전 실행조건을 맞춘다.
- `MEMORY_LIMIT`, `CPU_MAX_OCCUPY`, `MULTI_THREAD_ENABLE` 등 Mission 지정 환경변수로 장애 조건을 조정한다.
- OOM은 메모리 상승 패턴, 종료 직전/직후 로그, MemoryGuard 관련 근거, LIMIT 변경 전후를 남긴다.
- CPU는 특정 프로세스 CPU 상승, Watchdog 종료 근거, CPU_MAX_OCCUPY 변경 전후를 남긴다.
- Deadlock은 PID 생존, CPU/MEM 정체, 로그 정지, 스레드/락 대기 근거와 MULTI_THREAD 설정 전후를 남긴다.
- 각 장애마다 GitHub Issue 형태의 기술 리포트를 작성한다.
- 리포트에는 현상, Evidence/Logs, Root Cause, Workaround, Before/After Verification이 포함되어야 한다.
- 스케줄링 알고리즘 추론은 Source에서 선택 과제로 확인되면 Backlog/Bonus로 분리한다.

## 6. G3 TEST

- OOM: 메모리 사용량 증가와 종료 조건 재현, LIMIT 변경에 따른 생존시간/결과 변화
- CPU: 프로세스 CPU 상승과 Watchdog/종료 근거, CPU_MAX_OCCUPY 변경 전후
- Deadlock: PID 생존 + 자원 정체 + 로그 정지 + 스레드 대기 근거, 설정 변경 전후
- 리포트 3건에 필수 섹션과 Evidence 링크가 모두 존재하는지 자동/수동 검증

실제 장애 재현과 시스템 도구 결과는 환경상 AI가 수행할 수 없으면 `NEEDS-RUNTIME`으로 정확히 넘긴다.

## 7. G4 REVIEW

- 3개 케이스가 서로 다른 장애 원인을 증거로 구분하는가
- 단순 재부팅/추측이 아니라 관제·로그 근거가 있는가
- Workaround와 Root Cause를 혼동하지 않는가
- Before/After가 수치·로그·스크린샷으로 비교 가능한가
- BLOCKER=0, MAJOR=0인가

## 8. G5 RUNTIME / G6 EVIDENCE

Evidence 최소 후보:

- OOM: monitor 메모리 수치, 종료 로그, LIMIT 변경 전후
- CPU: top/ps/관제 캡처, 종료 로그, CPU_MAX_OCCUPY 전후
- Deadlock: PID, 스레드/CPU/MEM 정체, 마지막 로그, 설정 전후
- 각 GitHub Issue 또는 Markdown report 링크

## 9. G7 LEARN

- Memory Leak/OOM 영향
- 특정 프로세스 CPU 과점유와 시스템 지연
- Deadlock 4대 조건과 진단 근거
- 로그·관제 데이터를 이용한 장애 커뮤니케이션
