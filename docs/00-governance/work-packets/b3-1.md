## 3. Mission-derived Scope

- CLI 기반 Mini Redis를 구현한다.
- String 명령: `SET`, `GET`, `DEL`, `EXISTS`, `DBSIZE`, `KEYS`.
- 메모리 명령: `CONFIG SET maxmemory`, `INFO memory`.
- TTL 명령: `EXPIRE`, `TTL`.
- REPL에서 명령 파싱 → 실행 → 출력이 반복 동작한다.
- Hash Map은 직접 설계한 hash function과 chaining 방식으로 구현한다.
- LRU 추적을 위해 doubly linked list를 직접 구현한다.
- TTL 만료 관리를 위해 min-heap을 직접 구현하고 heapify up/down을 가진다.
- `SET`/성공한 `GET`은 LRU를 갱신하며, 만료된 GET은 삭제 후 LRU 갱신하지 않는다.
- 기존 키를 `SET`으로 덮어쓰면 기존 TTL을 초기화한다.
- `DEL`은 데이터/TTL/LRU 모든 구조에서 엔트리를 제거한다.
- maxmemory 초과 시 LRU 기준 자동 eviction을 수행하고 메모리 사용량/evicted count를 추적한다.
- 내장 `dict` 등으로 핵심 자료구조를 대체하는 방식은 Source 제한을 확인하여 금지한다.

## 6. G3 TEST

- 모든 필수 명령 정상/오류 케이스
- hash collision이 발생해도 값이 정확히 유지되는지
- LRU 순서가 SET/GET에 따라 갱신되는지
- maxmemory 초과 시 올바른 LRU key가 제거되는지
- EXPIRE/TTL 만료 전후 값
- 만료된 GET의 자동 삭제와 LRU 미갱신
- overwrite 시 TTL 초기화
- DEL 시 data/LRU/TTL 동시 제거
- DBSIZE/KEYS가 만료 상태와 일관적인지
- heap boundary 및 빈 구조 처리

## 7. G4 REVIEW

- O(1) LRU를 설명할 수 있는 구조인가
- TTL heap과 실제 데이터가 stale entry로 꼬이지 않는가
- eviction 후 메모리 값이 정확한가
- 핵심 자료구조가 내장 구조로 우회되지 않았는가
- BLOCKER=0, MAJOR=0인가
